Overview

What is the Aircraft Optimizer?

Aircraft Optimizer is a Vortex Lattice Method (VLM) solver for the aerodynamic analysis of low Reynolds number, multi-surface aircraft, built as the physics core of a multidisciplinary design optimization (MDO) framework. It aims to replace an existing in-house lifting-line method implemented in MATLAB, which had become a limiting factor on the range of aircraft configurations the optimizer could explore. The solver itself is developed as a standalone Julia package (MyPackage), with analysis scripts and documentation layered around it in the same repository.

The project spans two layers of rework, tackled together: a new aerodynamic formulation (vortex lattice in place of lifting line) and a new software architecture (a typed, struct-based Julia design in place of MATLAB's functional style), so the solver can sit inside an outer optimization loop that repeatedly reconfigures, re-analyzes, and post-processes candidate aircraft.

Key Engineering Decisions

Four calls that shaped the solver

Four major design choices were made at conceptual phase to give the initial design direction: each one a trade-off between accuracy, performance, and implementation complexity.

Vortex Lattice over lifting-line

Lifting-line theory couldn't represent low aspect ratio, highly swept, or multi-surface aircraft. VLM removes those restrictions while staying cheap enough to call repeatedly inside an optimization loop, which would be unfeasible with full CFD.

Julia over MATLAB/Python

Chosen for JIT-compiled performance close to compiled languages without giving up high-level, mathematical syntax. Additionally, Julia's threading capabilities make it suitable for parallel execution, which is essential since the solver runs many times per optimization cycle, not once.

Vortex rings over horseshoes

Rings calculate chordwise circulation gradients directly and capture camber influence more accurately, trading the simplicity of a purely horseshoe-based scheme for accuracy.

Immutable geometry, mutable results

Splitting the aircraft into an immutable Plane and a mutable Data field closes off an entire class of bugs where a geometry edit silently invalidates results already computed for it, while still allowing data to be updated through lazy simulation.

Motivation

Where the lifting-line method broke down

The existing MATLAB lifting-line implementation had accumulated constraints that increasingly conflicted with the aircraft configurations the optimization needed to explore. Sections were defined at a fixed, hardcoded number of spanwise stations linearly connected, which made elliptical and other continuously-varying planforms unrepresentable. The underlying theory itself also broke down for low aspect ratio wings and could not model multi-surface aircraft (e.g. wing-tail or wing-canard interaction) at all.

Separately, MATLAB's functional programming structure was limiting the post-processing side of the workflow: plotting, storing results, re-running a given configuration, and carrying one configuration across different types of analyses. They all required redefining and resimulating the plane and wouldn't allow more than one design to be analyzed simultaneously, which was inefficient and error-prone. A new object-oriented design was needed to support a more robust and scalable workflow.

01 Support arbitrary chord, twist, dihedral, and sweep distributions defined continuously along the span, rather than at a fixed number of linearly-connected sections.
02 Represent planforms, including elliptical wings, that lifting line's linear-section interpolation could not capture.
03 Extend validity to low aspect ratio wings and multi-surface aircraft, both outside lifting-line theory's assumptions.
04 Move to an object-oriented design that supports reproducible configuration storage, rerunning, and result post-processing.
05 Keep high-level, readable syntax while reaching near-compiled performance, since the solver needs to run repeatedly inside an outer optimization loop.

Method & Language Selection

Choosing VLM and Julia

Addressing the lifting-line limitations meant researching alternative aerodynamic formulations capable of handling swept, tapered, dihedral, low aspect ratio, and multi-surface geometries without the section-count restrictions of the existing code. The Vortex Lattice Method met these requirements: it discretizes each lifting surface into a grid of vortex elements rather than a single spanwise line of circulation, which removes the planform restrictions inherent to lifting-line theory while remaining a potential-flow method (cheap enough to sit inside an optimization loop, unlike higher-fidelity CFD).

Language choice: Julia was selected as a balance between high-level, mathematical syntax and just-in-time compiled performance. The solver needed to be readable and fast to iterate on during development, while still being fast enough at runtime to be called inside an optimization loop. A combination MATLAB's interpreted functional style and Python's dynamic typing both fall short of without additional tooling.

Numerical Foundation

Reusable building blocks

Rather than writing numerical methods inline wherever needed, common operations drawn from my MIE235 coursework, were implemented once as callable structs and reused throughout the solver and its pre/post-processing.

Spline struct

Takes a set of data points and returns a callable spline function as a struct, used to interpolate airfoil geometry and spanwise properties.

Least-squares regression struct

Fits a regression to a data set following the same callable-struct pattern as the spline utility.

Interpolation struct

General-purpose interpolation utility, structured the same way as the spline and regression structs for a consistent calling convention.

Gauss-quadrature integrator

A struct that takes a function once at construction, then integrates it over arbitrary limits via a simple call, e.g. integrator(a, b).

IO module

Handles input/output operations used in the solver. For example, reading and processing airfoil coordinate (.dat) files for use in mesh generation and camber-line interpolation.

MyPlots module

Visualization built on Plots.jl for 2D airfoil verification plots and GLMakie.jl for 3D visualization of the assembled aircraft mesh.

Aircraft Representation

Plane, Data, and Surface

A Plane is an immutable struct holding the list of Surface objects that make it up, plus a mutable Data field for anything that can only be known after analysis, including force and moment coefficients, static margin, stall and trim angles, and maximum takeoff weight. Keeping the plane's geometry immutable while isolating analysis outputs in a separate mutable field was a deliberate choice: it prevents a geometry mutation from silently invalidating results already computed for that configuration, which could otherwise mislead downstream analysis.

Each Surface is defined by the position of its root leading edge, its span, a list of airfoils together with their spanwise positions for interpolation, and chord, twist, dihedral, and sweep each defined as a function of the spanwise fraction rather than as fixed values at discrete stations. Boolean flags mark whether a surface is mirrored about the aircraft centerline or vertical (e.g. a fin), so a single Surface definition covers both planar lifting surfaces and vertical stabilizers.

Mesh Generation

From unit square to aircraft geometry

Each surface's mesh is built starting from a flat, normalized unit square, with a cosine distribution applied to cluster panels toward the leading and trailing edges and toward the tips, which is a standard VLM practice for resolving the higher gradients in circulation near those regions. Airfoil camber lines are interpolated across the defined sections and layered onto the flat mesh, after which the sweep, dihedral, and twist transformations, each defined as a function of span fraction, are applied at every spanwise station. The final mesh is returned as an array laid out for column-major access, matching Julia's native memory layout for the linear algebra performed in the solver.

Solver Formulation

Vortex ring implementation

The solver takes an assembled Plane along with the wind direction, a ground-effect flag, and altitude, and returns the aerodynamic solution for that condition.

Ring vs. horseshoe formulation: the solver uses ring vortices rather than horseshoe vortices for the bound elements, with the front bound segment placed at the panel's 25% chord, the collocation point at 75% chord, and the aft segment coincident with the front segment of the next chordwise ring. This was chosen for the additional accuracy of the ring formulation over horseshoes while keeping the overall implementation simple, since a purely horseshoe-based scheme would require separate treatment for chordwise circulation gradients that the ring formulation captures directly.

The wake shed from the trailing edge is modeled as horseshoe vortices carrying the same circulation as the trailing-edge rings. The geometry-dependent component of the aerodynamic influence coefficient (AIC) matrix is assembled once per configuration and cached, since it is reused unchanged across multiple angles of attack for the same geometry; wake influence is then added and the right-hand side is computed for each flow condition. Solving the resulting linear system gives the ring circulations, from which forces are recovered two ways — via the Kutta-Joukowski theorem and via the Trefftz-plane method, the latter used specifically for induced drag, before being projected into aircraft axes and used to compute moments and the corresponding aerodynamic coefficients.
